## 验收环境

- Go 1.27.1、Node 26.10.0、npm 12.2.0；应用进程 `GOMAXPROCS=2`。环境 cgroup 总 CPU 配额为 4 核（`cpu.max=400000 100000`）、总内存配额 32 GiB（`memory.max=34359738368`），进程增加不等于获得额外独占 CPU。

- 基线 API 18090 / 18091，候选 API 18092 / 18093；读写使用各自独立数据库和 Redis DB。正式读档串行执行，不与编译、浏览器或写负载同时运行。

- PostgreSQL 18 使用独立 tmpfs 容器、384 MiB 容器限额、32 MiB shared_buffers，验证新队列兼容性，不作为 MySQL 性能结论。
- 原工作盘满后，将当前工作副本与可重建缓存放在独立 `/tmp` 文件系统中；保留原开发数据库、媒体、密钥及基线。验收记录中的 `/tmp` 路径为本次工作区证据，复测应重新生成，不能假设跨环境保留。

最终代码的 `go test -p 2 ./...` 通过：87 个测试包、8 个无测试包；前端 73 个测试文件 / 342 项通过，`npm run lint` 与 `npm run build` 通过。全量回归曾暴露既有异步上传测试在处理结束后仍检查 processing 的竞态，已用明确的工作发布屏障修复，连续 20 次及全包复验通过，没有修改生产上传行为。最后新增列表变更／删除的账号和路由隔离、关注话题的迟到响应、新帖提示保留正文、回应者弹窗关闭／重开／失败，以及头像加载错误和切换隔离回归。最后补充的 10 项表情回应回归覆盖账号／帖子切换，以及详情关闭重开后的迟到成功、错误和 finally 状态，防止旧请求覆盖新窗口。

- 每个操作最多 20 秒，SQL 租约 30 秒；采用短工作单元与接管，不让单次工作无限续租。
