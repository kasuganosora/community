# 时间线性能与正确性验证

本次验证使用独立的 MySQL 数据库和 Redis DB，未向真实联邦实例灌入压测帖子。基准来自提交 `8e7e284` 的冻结可执行文件，优化版本使用相同数据、运行参数和请求路径。日期：2026-10-03。

## 工作负载

- 2,000 个账号、60,000 条帖子、6,400 条关注关系、8,571 个媒体引用和 10,000 条表情回应。
- 数据包含回复、转发、标签、列表、四种可见范围、屏蔽、静音及封禁账号。查看者关注 200 个账号，列表包含 50 个账号；另建同名但成员不同的列表检查缓存隔离。
- 转发指向真实公开原创，避免人工生成嵌套转发链而改变可返回内容。最终成对测量使用相同修正后的数据；早期探索结果另行保留，不混入最终对比。
- 测试首页、公共、公共媒体、个人、列表、标签共六种时间线，每页 20 / 40 条，并发 1 / 8 / 32；另测 Redis 冷缓存及 `max_id=30000` 的深分页。
- 应用 `GOMAXPROCS=2`，环境 CPU 配额 4 核；MySQL 最大连接 100、空闲连接 10。保留其他实验服务，测量期间暂停编译及浏览器负载。
- 使用持续 HTTP/1.1 连接的闭环客户端。每个常规组合持续 3 秒，延迟包含接收完整响应，吞吐包含客户端 JSON 校验。结果未进行 coordinated omission 修正，不代表开放到达率下的容量上限。

“冷缓存”只清空独立 Redis DB，MySQL buffer pool 和系统文件缓存保持温热。单次冷请求不是冷缓存并发压测。个人账号仅有 30 条帖子，40 条分页返回不足 40 条可以是正常耗尽。

## 实测结果

最终版本完成 48 个场景、13,167 次请求，HTTP、传输及业务语义检查错误均为 0。另有 26 项权限与分页校验、18 份包含转发原帖的页面样本全部通过。最终二进制 SHA256 为 `a73c68e89de3e398e7984c05bdd90eb1434b8ad3455c754b279e475f25611cd2`，结果标识为 `candidate-queryshape-flat`。

Redis 冷缓存的等价单请求：首页 169.058 → 44.209 ms，列表 117.495 → 20.796 ms。这是各一次观测，MySQL 与系统缓存仍温热。

## 优化内容

缓存重建在内存计算转发聚合后批量写入 Redis，同一个进程内相同时间线的并发缓存缺失共享重建工作。缓存保留候选 ID，读取时复核当前列表成员、关注、屏蔽、封禁和转发原帖权限；没有添加跨请求的权限结果缓存。

所有 ID 游标采用不包含边界的比较，数据库排序与游标统一使用 ID。被过滤的候选页继续向后读取；个人时间线在数据库限量前过滤受众，转发原帖不可见时继续补页。列表使用带版本前缀的数值 ID 缓存键，避免同名列表及旧数字标题缓存互相覆盖。请求取消传递至 Redis、数据库和序列化阶段。

标签与媒体关联采用带 `LIMIT 1` 的相关标量子查询，使 MySQL 沿帖子 ID 倒序查找已有索引并尽早满足页大小。实际执行计划显示，原来的半连接会先扫描数千条关联、再排序选页。修改保留全部受众及静音条件，多个附件或重复标签关联不会产生重复帖子；没有添加索引或迁移。

标签先通过现有 `tag_id` 索引有界读取最多 513 个关联 ID：空标签直接排除，不超过 512 条的标签使用 ID 集合查询，较大标签才采用标量查询。这避免少量旧帖的标签为了确认页已结束而扫描整段帖子历史。该策略不是所有分布下的最优计划；较大但集中于很久以前的标签仍需结合实际数据评估覆盖索引。

候选筛选通过后，原帖与转发原帖的展示关联一次批量加载。序列化按整页批量处理账号资料中的表情、互动状态和转发原帖字段，正文只渲染一次。五种互动状态和作者静音查询用 `UNION ALL` 合为一次数据库往返。投票统计在 SQL 聚合，只加载当前查看者的具体投票记录；没有投票的页面直接跳过投票查询。

`tootctl feeds build` 复用相同重建逻辑，并修复旧 CLI 写入的时间戳分数，使其与 ID 游标一致。原先的逐项 Redis 写入及单独实现的受众条件不再保留。

网页在切换账号时清空时间线并拒绝旧请求的迟到响应，分页按外层帖子 ID 去重并检测游标停滞。列表、标签和个人页切换目标时重置分页，加载结束后仍在视口中的哨兵继续触发加载。富文本保留 HTML 清理，只去掉重复的一次清理。

## 测量与验收规则

不能把空页、遗漏帖子或放宽权限产生的速度提升算作优化。每次测量同时记录 HTTP 错误、返回条数及固定数据集的业务校验结果。旧版本的媒体空页、封禁账号未过滤、深分页成员错误等结果单独作为修复证据，不计算有效吞吐提升。

完整 HTTP 测量之外还检查 SQL 数量及传输行数。批量序列化的定向测试中，20 / 80 条帖子均使用 8 次 SQL；40 次相同资料表情查询由 40 次降到 1 次。1,002 条投票记录只返回 1 行聚合及查看者自己的 2 行投票。这里的查询数不包含 HTTP 鉴权、时间线选择及关联预加载，不能与整页 HTTP 查询数混用。

完整关联的定向测试从 30 次查询降到 15 次，对返回模型进行 JSON 深比较，确认原帖、转发及附件、投票、表情、提及、回复对象等数据一致。

最终源码的完整 Go 回归通过 71 个测试包、6,548 项测试，42 项按环境条件跳过。前端 36 个文件、137 项测试以及 lint、生产构建通过。浏览器连续加载 220 条唯一帖子仅发出 11 次请求；五类页面的分页正常。账号切换测试验证 20 条私信对另一账号均返回 403，旧账号的迟到响应不会恢复旧卡片。页面仍采用完整列表渲染，220 条时约 18,625 个 DOM 节点；没有宣称虚拟列表或 DOM 复杂度改善。

最终二进制已部署到开发服务与联邦实验环境的 Community。Community、Misskey、Mastodon、Synapse 的 HTTPS 应用检查通过。私有令牌、数据库配置和浏览器原始资料保留在实验目录，不进入仓库。

## 复现

仓库提供仅依赖 Python 标准库的 [压测脚本](../scripts/benchmark-timelines.py) 和[参数说明](../scripts/benchmark-timelines.md)。脚本只发 GET，不创建数据、清缓存或管理进程。认证令牌从环境或仓库外私有文件读取，不写入结果。

```sh
python3 scripts/benchmark-timelines.py --url http://localhost:8080 \
  --cases public media --concurrency 1 8 32 --limit 20 40 \
  --duration 3 --output /tmp/timeline-results.json
```

这个通用脚本只检查结构、条数、重复 ID 和游标；受众、列表成员及预期完整性必须根据自己的数据单独验证。比较时固定数据库、二进制、连接池、日志模式、CPU 配额和缓存状态，保留每轮原始结果。
